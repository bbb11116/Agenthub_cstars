# Vibe Coding — 对话式编程方法论

基于 AgentHub 项目的实战开发经验，提炼出的人机协作编程方法论。核心理念：**你说方向，AI 走路；你说症状，AI 看病；你说验收标准，AI 循环到通过。**

## When to Use

- 使用 AI 辅助进行软件开发
- 需要快速搭建复杂系统
- 遇到 bug 需要 AI 协助排查
- 需要从零开始构建项目
- 需要 AI 帮忙做技术选型和架构设计

## When Not to Use

| 场景 | 建议 |
|------|------|
| 完全不懂技术，无法判断 AI 输出质量 | 先学习基础，再用 AI 辅助 |
| 安全敏感的生产环境代码 | 人工逐行审查，不能盲信 AI |
| 需要极致性能优化的底层代码 | AI 倾向过度设计，需人工主导 |

## 〇、方案对齐：动手前的"双向澄清"（最重要）

**这是整个方法论中最关键的一步。** 在写任何代码之前，先完成一轮"提出方案 → 反向提问 → 回答澄清 → 确认方案 → 执行"的完整循环。这一步能避免 80% 的返工。

### 流程图

```
人类提出需求
    ↓
AI 给出 2-3 个候选方案 + 推荐
    ↓
AI 反向提问："在确定方案前，你能不能告诉我......"（3-5 个关键问题）
    ↓
人类回答问题
    ↓
AI 综合信息，给出最终确认方案
    ↓
人类明确："可以，开始执行"
    ↓
AI 实施
```

### 为什么这一步至关重要

| 没有对齐就动手 | 先对齐再动手 |
|---------------|-------------|
| 做完发现需求理解错了，返工 | 一次到位，零返工 |
| AI 选的技术方案你不熟悉，维护困难 | 方案经过你确认，技术栈符合预期 |
| 隐藏的需求细节被忽略 | 关键边界条件被显式讨论 |
| AI 过度设计或设计不足 | 设计深度匹配实际需求 |
| 协作变成"投骰子" | 协作变成"联合设计" |

### AI 应该怎么"反向提问"

**核心原则：问出那些不问就一定会踩坑的隐藏信息。**

**问题应该覆盖的维度：**

```
1. 范围边界：哪些场景需要支持？哪些明确不需要？
2. 优先级：完美完成核心功能 vs 快速跑通全部功能？
3. 兼容性：要和现有哪些模块/数据格式兼容？
4. 性能/规模：预估的数据量、用户量、并发量？
5. 失败处理：哪些错误是致命的？哪些可以降级？
6. 验收标准：什么算"做完了"？什么算"做好了"？
7. 约束条件：不能用哪些技术/库？必须保留哪些接口？
8. 时间成本：希望快速出原型，还是一次性做完善？
```

**示例：群聊功能开发前的反向提问**

```
在开始实现之前，我有几个问题想和你确认：

1. 群聊的初始版本，需要支持 @ 指定 Agent，还是先只做自动分派？
2. 多 Agent 同时工作时，是否需要考虑它们的执行结果互相依赖（DAG），
   还是简单的并行各自完成即可？
3. 产物预览是只支持 Markdown，还是需要 HTML/PPT/PDF？
4. 旧数据/旧会话的迁移需要支持吗？还是全新开始？
5. 这个功能预计要支撑多少人同时使用？需要做并发控制吗？

回答完这些，我就可以给你一个最终方案。
```

### 人类应该怎么"回答问题"

**回答原则：**
- 不知道就明说"我不确定"或"你给建议"，不要瞎答
- 答案之间如果有矛盾，主动指出
- 回答后让 AI 复述一遍最终方案，确保理解一致

**反例：**
```
AI：需要支持 DAG 吗？
人：随便，你觉得怎么好就怎么设计  ❌
```

**正例：**
```
AI：需要支持 DAG 吗？
人：是的，需要支持。我现在群聊演示场景是3个Agent，
    任务有串行也有并行，最终要展示PPT和HTML。
    1cc2dee 这个提交已经基本搭好框架了，你可以参考。  ✓
```

### AI 的最终确认方案应该长什么样

收到人类回答后，AI 应该输出一个**结构化的确认文档**：

```
## 最终方案

### 目标
[用一句话说清要做什么]

### 技术选型
- [选什么，为什么]
- [选什么，为什么]

### 实现路径
1. [步骤1]
2. [步骤2]
3. [步骤3]

### 明确不做的事
- [不做什么，避免范围蔓延]

### 验收标准
- [ ] [可验证的条件1]
- [ ] [可验证的条件2]

### 风险点
- [可能出问题的地方]

确认这个方案 OK 吗？OK 我就开始实现。
```

### 常见错误模式

**错误 1：AI 不问就动手**
```
❌ AI：收到需求 → 立刻写代码
✅ AI：收到需求 → 先问 3-5 个关键问题 → 确认方案 → 写代码
```

**错误 2：AI 问太多无关紧要的问题**
```
❌ AI：你的项目用了什么字体？配色方案是什么？
✅ AI：核心功能边界？性能要求？兼容性约束？
```

**错误 3：人类跳过对齐环节**
```
❌ 人：需求说完 → "直接做吧，别问了"
✅ 人：需求说完 → 认真回答 AI 的问题 → 确认方案
```

**错误 4：方案确认后还反复修改方向**
```
❌ 确认用方案A → 实现到一半 → 改成方案B → 又改回方案A
✅ 确认前充分讨论 → 确认后坚定执行 → 真有问题再调整
```

### 这步看似"浪费时间"，实际是"最高效"

| 阶段 | 看起来耗时 | 实际效果 |
|------|------------|----------|
| 跳过对齐 | 5 分钟 | 返工 2 小时 |
| 完整对齐 | 20 分钟 | 一次到位 |
| 深度对齐 | 45 分钟 | 获得最佳方案 + 零返工 |

**心法：花在讨论方案上的 20 分钟，能省下 2 小时的实现和返工。**

## 一、提问策略

### 1.1 描述"要什么"，不描述"怎么做"

**差的提问：**
```
帮我写一个函数，接收 conversationId 参数，先查数据库判断类型，
然后如果是 group 就调用 handleGroupUserMessage，否则调用 handleSingleUserMessage
```

**好的提问：**
```
用户发消息时，系统需要自动判断是单聊还是群聊，走不同的处理逻辑
```

**原理：** AI 比你更了解代码库结构。你描述意图，AI 找到最佳实现路径。你描述步骤，反而限制了 AI 的发挥。

### 1.2 用具体场景代替抽象需求

**差的提问：**
```
帮我做一个群聊功能
```

**好的提问：**
```
帮我做一个群聊功能，用户可以在群里 @ 指定 Agent 回答问题，
也可以不 @ 让系统自动分派。多个 Agent 可以同时工作，
有的先做有的后做，最后汇总结果。
```

**原理：** 具体场景让 AI 理解你的预期效果，避免做出不符合想象的东西。

### 1.3 给约束条件，不给实现细节

**差的提问：**
```
用 Redux 管理状态，在 src/store 下创建 index.ts，
用 createSlice 定义 chatSlice...
```

**好的提问：**
```
状态管理要支持实时更新，Agent 执行状态变化时前端要立刻反映出来。
项目用的 React。
```

**原理：** 约束条件框定范围，实现细节留给 AI。AI 可能会选择更好的方案（比如事件驱动而非 Redux）。

### 1.4 一次一个阶段，不要一口气全说完

**差的提问：**
```
帮我做一个完整的 AI Agent 平台，支持单聊、群聊、DAG调度、
多模型接入、产物预览、PPT生成、技能系统...
```

**好的提问：**
```
第一阶段：先做一个能和 AI 对话的单聊功能
（验收通过后再进入下一阶段）
```

**原理：** 增量开发，每步验收。一次说太多，AI 会过度设计，你会失去控制。

## 二、调试对话策略

### 2.1 描述症状，不猜测原因

**差的调试提问：**
```
我觉得是数据库连接池满了，帮我改连接池配置
```

**好的调试提问：**
```
群聊发消息后没反应，控制台没有报错，但 Agent 没有启动。
单聊是正常的。
```

**原理：** 你描述现象，AI 来诊断。你的猜测可能是错的，会误导 AI 走弯路。

### 2.2 提供上下文，越具体越好

**好的调试提问模板：**
```
[现象] 群聊发消息后 DAG 面板不显示
[环境] macOS, Electron, 使用 builtin_openai provider
[复现步骤] 1. 创建群聊 2. 添加3个Agent 3. 发送任务消息
[期望] 显示 DAG 可视化面板
[实际] 只显示一条消息，没有调度发生
[已知信息] 单聊正常，群聊的 handleGroupUserMessage 被调用了
```

**原理：** AI 看不到你的屏幕。你提供的信息越多，AI 定位问题越快。

### 2.3 让 AI 先探索，再修复

**好的调试流程：**
```
你：群聊调度失败了
AI：我来看看 dispatchService 的逻辑（探索代码）
AI：发现问题在 XXX（诊断）
你：确认，修吧
AI：已修复（实施）
你：验证通过 / 还有问题
```

**原理：** 不要直接让 AI 改代码。先让它看懂问题，再动手。盲目修改会导致更多 bug。

### 2.4 修复后追问"为什么"

**好的追问：**
```
这个 bug 的根本原因是什么？以后怎么避免类似问题？
```

**原理：** AI 会分析根因，帮你建立心智模型。下次遇到类似问题，你能更快定位。

## 三、迭代策略

### 3.1 渐进式复杂度

```
最简可用 → 核心功能 → 高级特性 → 生产就绪
```

AgentHub 的实际迭代路径：
```
Mock 单聊 → 真实单聊 → 群聊基础 → DAG 调度 → 多模型接入 → 产物预览
```

**原理：** 每一步都是可运行的。任何时候停下来，都有一个能用的东西。

### 3.2 先跑通再优化

**第一轮：** 让它能跑
```
先实现最简版本，能跑就行
```

**第二轮：** 让它跑得好
```
现在性能不好，帮我优化 DAG 布局算法
```

**第三轮：** 让它跑得稳
```
边界情况没处理，比如 Agent 超时、输出为空、JSON 解析失败
```

**原理：** 过早优化是万恶之源。先验证方向，再打磨细节。

### 3.3 每个阶段都验收

**验收清单模板：**
```
□ 功能正常：[描述核心功能]
□ 边界处理：[描述异常情况]
□ 用户体验：[描述交互感受]
□ 代码质量：[描述可维护性]
```

**原理：** 不验收就进入下一阶段，问题会指数级累积。

## 四、协作边界

### 4.1 人类决策，AI 执行

| 人类负责 | AI 负责 |
|----------|---------|
| 做什么 | 怎么做 |
| 技术选型方向 | 具体实现方案 |
| 优先级排序 | 代码组织 |
| 验收标准 | 测试用例 |
| 安全边界 | 代码质量 |

### 4.2 设置硬性边界

在协作开始时，明确告诉 AI 你的底线：

```
- 不要把密钥写到代码文件里
- 不要引入新的 npm 包，除非我同意
- 不要修改我还没看过的文件
- 不要删除看起来"没用"的代码
```

**原理：** AI 有时会"热心过度"。明确边界，避免意外。

### 4.3 知道什么时候自己动手

AI 不擅长的事：
- 复杂的 UI 微调（像素级还原）
- 性能敏感的底层优化
- 需要运行时调试的问题（AI 看不到运行时状态）
- 涉及外部服务的集成测试

**原理：** AI 是强大的助手，但不是万能的。知道边界，才能高效协作。

## 五、对话模板库

### 5.1 新功能开发

**第一步：人类提需求**
```
我想做一个[功能名]，核心需求是：
1. [需求1]
2. [需求2]
3. [需求3]

约束条件：
- [约束1]
- [约束2]

先别写代码，给我一个方案，方案里要有：
1. 你打算怎么实现（关键技术决策）
2. 你有哪些没搞清楚、需要问我的
```

**第二步：AI 反向提问**
```
在开始前我有几个问题：
1. [范围边界问题]
2. [优先级问题]
3. [兼容性/性能问题]
4. [验收标准问题]
```

**第三步：人类回答 + AI 确认方案**
```
基于你的回答，最终方案是：
- 目标：
- 技术选型：
- 实现步骤：
- 明确不做的事：
- 验收标准：
- 风险点：

OK 的话我开始实现。
```

**第四步：人类明确"OK，开始"**
```
可以，开始执行
```

### 5.2 Bug 修复

```
遇到一个问题：
- 现象：[描述现象]
- 复现：[步骤]
- 期望：[应该怎样]
- 实际：[实际怎样]
- 已知：[你已经排查的信息]

帮我定位原因。
```

### 5.3 代码审查

```
看看这个文件/模块的代码，有没有：
- 逻辑漏洞
- 性能问题
- 不符合项目风格的地方

只报告问题，不要自动修改。
```

### 5.4 架构讨论

```
我在考虑[方案A]和[方案B]，各自的优劣是什么？
我的场景是[描述场景]，你推荐哪个？
```

### 5.5 学习理解

```
帮我解释一下这段代码的工作原理：
[代码片段]

重点解释：
- 数据流是怎么走的
- 关键设计决策是什么
- 有什么容易踩的坑
```

## 六、效率提升技巧

### 6.1 利用 AI 探索代码库

```
帮我梳理一下这个项目的整体架构，画一个模块依赖图
```

AI 会遍历代码库，生成架构概览。比你自己读代码快 10 倍。

### 6.2 让 AI 写测试

```
给这个函数写单元测试，覆盖正常情况和边界情况
```

AI 写测试又快又全，你只需要审查。

### 6.3 批量操作交给 AI

```
把所有文件里的 oldFunctionName 改成 newFunctionName
把所有的 console.log 替换成 logger.debug
```

AI 做批量重构又快又准。

### 6.4 让 AI 帮你做技术选型

```
我需要一个轻量级的状态管理方案，项目是 React + TypeScript，
不需要 Redux 那么重。有什么推荐？
```

AI 会给出对比分析，你做最终决策。

## 七、常见误区

### 误区 1：把 AI 当搜索引擎

```
❌ "JavaScript 的 map 函数怎么用"
✅ "帮我把用户列表转换成下拉框的选项格式"
```

AI 不是文档。告诉它你要什么结果，它会帮你写代码。

### 误区 2：一次性给太多需求

```
❌ "帮我实现用户系统、权限管理、数据导出、报表生成..."
✅ "先实现用户注册登录，我验收后再做权限"
```

分而治之，每步验收。

### 误区 3：不看 AI 的输出就继续

```
❌ AI 写完代码 → 直接说"继续"
✅ AI 写完代码 → 阅读理解 → 验收测试 → "通过，继续"
```

你不看代码，AI 就是在盲写。

### 误区 4：遇到问题就换 AI

```
❌ "这个 AI 不行，换个试试"
✅ "这个问题你没理解我的意思，我换个说法..."
```

大多数时候是沟通问题，不是 AI 能力问题。

### 误区 5：完全依赖 AI，自己不学习

```
❌ AI 写完代码 → 完全不看 → 直接用
✅ AI 写完代码 → 理解原理 → 自己能维护
```

AI 是助手，不是替代品。理解代码才能维护代码。

## 八、Vibe Coding 心法总结

```
先对齐，再动手（方案 + 反向提问 + 确认）
说意图，不说步骤
说症状，不说药方
说约束，不说实现
分阶段，逐步验收
设边界，控制风险
先跑通，再优化
让 AI 探索，你做决策
```

**核心原则：你是船长，AI 是水手。你决定去哪里，AI 负责怎么划船。**

**最重要的第一步：动手前先对齐方案。** 花 20 分钟讨论，能省 2 小时返工。
