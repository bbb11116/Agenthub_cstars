# 决策日志 — AgentHub 项目

本日志记录项目开发过程中的关键技术决策，每个决策包含：背景、候选方案、最终选择、决策理由。

## 决策 #1：Agent 运行时架构（05-27）

**背景：** 需要支持多种 AI Agent 引擎（Codex、Claude Code、内置 LLM），但不同引擎的调用方式差异巨大。

**候选方案：**
| 方案 | 优势 | 劣势 |
|------|------|------|
| A. 直接在业务代码里调用各引擎 | 简单直接 | 耦合严重，难以扩展 |
| B. 适配器模式（Adapter Pattern） | 解耦，可扩展 | 初期抽象成本略高 |
| C. 统一封装为 CLI 调用 | 隔离最彻底 | 性能损失，灵活性低 |

**最终选择：** 方案 B — 适配器模式

**决策理由：**
- 不同引擎的协议（HTTP、SSE、CLI 流）差异大，适配器能统一抽象
- 未来新增引擎只需实现 `AgentAdapter` 接口，零侵入
- 业务逻辑只依赖接口，方便测试和替换

**影响：**
- `src/shared/agentAdapter.ts` 定义 `AgentAdapter` 接口
- `src/main/services/adapters/` 目录存放各引擎适配器
- `src/main/services/llmProviderAdapters.ts` 统一调度

**协作过程：**
- 人类提出："要支持多种 Agent 引擎"
- AI 给方案并反向提问
- 人类确认"用适配器模式"
- AI 实现

## 决策 #2：群聊调度模式选型（05-29）

**背景：** 群聊场景下，多个 Agent 如何协作完成任务？需要明确调度模式。

**候选方案：**
| 方案 | 描述 | 适用场景 |
|------|------|----------|
| A. 顺序执行 | 一个 Agent 完成后再下一个 | 强依赖任务 |
| B. DAG 调度 | 显式声明依赖关系，调度器解析 | 混合串并行 |
| C. 全部并行 | 一次性启动所有 Agent | 独立任务 |

**最终选择：** 方案 B — DAG 调度（默认），并提供 sequential 模式作为退化方案

**决策理由：**
- 比赛演示需要展示"任务分派"和"产物生成"，串行不足以体现复杂度
- 实际业务中"先调研再分析""同时生成 HTML 和 PPT"等场景大量存在
- DAG 能统一表达顺序执行和并行执行

**影响：**
- `src/shared/groupChat.ts` 定义 `DispatchMode` 和 `ExecutionMode` 类型
- `src/main/services/dispatch/agentScoring.ts` 实现 `buildExecutionBatches` 算法
- `src/renderer/features/chat/GroupRunTimeline.tsx` 实现 DAG 可视化

**协作过程：**
- 人类提出群聊需求时强调"任务有串行也有并行"
- AI 调研现有代码后提出 DAG 方案
- 人类确认方案后实施
- 经过 1 天实现 + 1 天 bug 修复后稳定

## 决策 #3：Agent 评分匹配算法（05-29）

**背景：** 编排器决定分派给哪个 Agent 时，需要有量化依据。

**候选方案：**
| 方案 | 评估维度 | 复杂度 |
|------|----------|--------|
| A. 随机选择 | 无 | 极低 |
| B. 简单关键词匹配 | capability 文本重叠 | 低 |
| C. 多维度加权评分 | 能力/工具/上下文/历史 | 中 |
| D. LLM 语义判断 | 全维度 | 高 |

**最终选择：** 方案 C 为主 + 方案 D 为辅

**决策理由：**
- 完全随机质量太差
- 纯关键词匹配对长描述不友好
- LLM 评分成本高、延迟大，不适合每轮都调用
- 折中：默认用加权评分，关键路径可触发 LLM 能力判断

**评分公式：**
```
finalScore = capabilityMatch × 0.4
           + toolMatch × 0.2
           + contextRelevance × 0.2
           + historicalReliability × 0.2
```

**影响：**
- `src/main/services/dispatch/agentScoring.ts` 实现评分逻辑
- `orchestratorRuntimeService.ts` 提供可选的 LLM 能力判断
- 失败时降级到 `fallbackCapabilityMatch`（关键词匹配）

**协作过程：**
- AI 提出方案时主动询问："评分权重应该怎么分配？"
- 人类回答："能力匹配最重要，给 0.4"
- AI 实施

## 决策 #5：子 Agent 输出截断策略（05-29）

**背景：** LLM 输出可能很长（数千 token），直接传给后续 Agent 会爆 token 限制。

**候选方案：**
| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 硬截断前 N 字符 | 简单 | 信息丢失 |
| B. 长输出生成 Artifact | 保留全文 | 复杂 |
| C. 流式分块 | 平滑 | 解析困难 |

**最终选择：** 方案 B + Manifest Repair

**决策理由：**
- 截断会丢失关键信息
- 长内容应作为独立 artifact 保留
- 后续 Agent 通过 artifact ID 引用，而非全文传递

**具体机制：**
1. 检测输出 > 1500 字符（`LONG_DELIVERABLE_ARTIFACT_THRESHOLD`）
2. 创建 Markdown artifact 保存完整内容
3. 触发"manifest repair"提示，让 Agent 返回简短 JSON 引用 artifact ID
4. 后续 Agent 通过 ID 查找完整内容

**影响：**
- `src/main/services/dispatchService.ts` 第 1105 行 `buildSubAgentPrompt` 实现
- `src/main/services/groupExecutionService.ts` 第 146 行 `parseSubAgentResult` 解析

**协作过程：**
- AI 在方案阶段主动指出 token 限制问题
- 人类确认"长内容用 artifact 引用"
- AI 实施

## 决策 #6：调度并发控制（05-30 bug 修复）

**背景：** 群聊调度时，如果用户连续发消息，会触发多个并发调度，可能导致状态错乱。

**候选方案：**
| 方案 | 机制 | 性能 |
|------|------|------|
| A. 全局锁 | 任意时刻只有一个调度 | 简单但慢 |
| B. 按会话锁 | 同一会话串行，不同会话并行 | 中等 |
| C. 消息队列 | 排队执行 | 复杂 |

**最终选择：** 方案 A — 调度级全局锁

**决策理由：**
- 群聊场景并发量低（一个用户一次只能发一条）
- 全局锁实现最简单，不易出 bug
- 未来可优化为会话级锁

**影响：**
- `src/main/services/conversationRunLock.ts` 实现锁机制
- `handleGroupUserMessage` 在入口处检查锁

**协作过程：**
- 人类反馈 bug："群聊发消息后状态错乱"
- AI 探索代码后定位到并发问题
- AI 提出方案，人类选择全局锁
- AI 实施

## 决策 #8：密钥管理（05-31 之后）

**背景：** 真实 LLM 需要 API Key，存哪里？

**候选方案：**
| 方案 | 存储位置 | 风险 |
|------|----------|------|
| A. 项目内 .env 文件 | 项目目录 | 易泄露到 git |
| B. ~/.zshrc | 用户 shell | macOS GUI 应用读不到 |
| C. ~/.zshenv | 用户 shell（所有 zsh） | 推荐 |
| D. 系统环境变量 | launchctl | GUI 应用可读 |

**最终选择：** 方案 C — `~/.zshenv`（macOS）

**决策理由：**
- 项目文件有 git 提交风险，绝对不能存
- `~/.zshrc` 仅交互式 shell 加载，Electron GUI 进程读不到
- `~/.zshenv` 在所有 zsh 进程中加载，包括 npm/Electron 启动的子进程

**影响：**
- 用户在 `~/.zshenv` 中配置 `AGENTHUB_*_API_KEY`
- `webToolService.ts` 等服务从 `process.env` 读取
- 形成项目级 memory 文件记录此约束

**协作过程：**
- 人类强调"密钥不能放项目里"
- AI 提出 `~/.zshrc` 方案
- 实测发现 GUI 进程读不到，改为 `~/.zshenv`
- 写入持久化 memory，避免下次重复踩坑

## 决策 #9：DAG 可视化布局算法（05-30）

**背景：** DAG 节点位置如何排布才清晰？

**候选方案：**
| 方案 | 算法 | 美观度 |
|------|------|--------|
| A. 力导向布局 | 物理模拟 | 高但抖动 |
| B. 分层布局（按依赖深度分列） | 拓扑排序 + 分层 | 中但稳定 |
| C. 自动 + 微调 | AI 辅助 | 高但成本高 |

**最终选择：** 方案 B — 分层布局

**决策理由：**
- 力导向布局每次刷新都会重排，影响阅读
- 分层布局位置确定，状态变化时易追踪
- 实施简单，CSS Grid 即可

**布局参数：**
```
节点尺寸：220 × 108 px
列间距：72 px
行间距：22 px
边样式：贝塞尔曲线 + 箭头
```

**影响：**
- `GroupRunTimeline.tsx` 第 491 行 `buildDagLayout` 实现
- `DagEdgeLayer` + `DagNodeCard` 组件组合渲染

**协作过程：**
- AI 提出方案时附上可视化草图
- 人类确认"分层布局够用"
- AI 实施

## 决策 #10：验收标准自动审查（05-30）

**背景：** 子 Agent 完成任务后，如何判断结果是否满足要求？

**候选方案：**
| 方案 | 机制 | 准确性 |
|------|------|--------|
| A. 人工审查 | 每次都看 | 高但慢 |
| B. LLM 自评 | Agent 评估自己 | 中 |
| C. 显式验收标准 + 自动重试 | 任务定义时声明标准 | 高 |

**最终选择：** 方案 C

**决策理由：**
- 比赛要求"最终产物"必须有保证
- 显式标准比隐式判断更可控
- 未通过可自动重试，最多 3 轮

**影响：**
- `groupExecutionService.ts` 第 409 行 `reviewAcceptanceCriteria` 实现
- `agentExecution.ts` 定义 `groupMaxRedispatchRounds: 3`

## 决策模式总结

### 高频决策模式

```
人类提出需求
    ↓
AI 调研代码 + 给出 2-3 个方案
    ↓
AI 反向提问关键不确定点（权重、范围、兼容性等）
    ↓
人类回答
    ↓
AI 给出最终方案（含验收标准）
    ↓
人类"OK，开始"
    ↓
AI 实施
```

### 关键经验

1. **架构级决策**（如 DAG vs 串行）需要充分讨论
2. **参数级决策**（如评分权重）快速决定即可
3. **Bug 修复决策**（如并发控制）以简单方案优先
4. **横切关注点**（如密钥管理）建立项目级规范

### 反向提问的典型维度

每次方案讨论前，AI 都会问这几类问题：
1. **范围边界**：哪些必须做，哪些明确不做
2. **优先级**：完美核心 vs 快速全功能
3. **验收标准**：什么算"完成"
4. **兼容性**：要和现有什么共存
5. **失败处理**：什么算"灾难"，什么可以降级
6. **约束条件**：禁止使用什么
